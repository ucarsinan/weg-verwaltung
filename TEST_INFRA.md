# E2E Test Infra: WEG-Verwaltungssoftware Track 2 & 3

## Test Philosophy
- Opaque-box, requirement-driven. Tests verify features from the user's perspective without depending on implementation details.
- Methodology: Category-Partition, Boundary Value Analysis (BVA), Pairwise Combinatorial Testing, and Real-World Workload Testing.

## Test Architecture
- **Test Runner**: Playwright E2E Test Runner (`@playwright/test`)
- **Invocation**: `pnpm --filter @weg-verwaltung/web exec playwright test`
- **Pass/Fail Semantics**: All active tests must run to completion with an exit code of 0.
- **Directory Layout**: Tests reside under `apps/web/e2e/`.
- **Authentication**: Auth state is seeded and shared through a local Playwright auth-state file generated by `e2e/auth.setup.ts`. Tests that require unauthenticated or different user contexts explicitly override `use.storageState`.
- **Migration Status Assumption**: Local migration files exist from `0001` through `0056`. Cloud migration state was not re-verified in this audit and must not be inferred from local files.
- **Cold-Storage Safety Gate**: Active tests must not expect tenant UI archive, detach, or drop behavior. Until a privileged export + manifest + HMAC-verify job exists, tests verify read-only visibility and destructive-action blocking.
- **Finance Model Assumption**: Option B is binding for Sollstellungen. Tests must treat `sollstellung` as historical, materialized unit-month targets: generation inserts missing rows idempotently, direct writes are blocked, and plan/unit/MEA changes do not rewrite existing rows.

## Detailed Test Cases

### Tier 1: Feature Coverage (Happy Path)
- **Feature 1: Audit Log Cold-Storage Readiness (Backend)**
  1. `audit-cold-storage-list`: Verify backend can list archivable partitions (>24 months old).
  2. `audit-cold-storage-no-tenant-archive`: Verify tenant-scoped code cannot start archive/export execution.
  3. `audit-cold-storage-detach-disabled`: Verify detach execution is disabled by the `0041` contract.
  4. `audit-cold-storage-drop-disabled`: Verify drop execution is disabled by the `0041` contract and no partition is removed.
  5. `audit-cold-storage-prevent-recent`: Verify partitions newer than 24 months are not considered archivable.
- **Feature 2: Audit Log Cold-Storage UI**
  1. `audit-ui-view-archivable`: Verify the `/audit` page lists archivable partitions.
  2. `audit-ui-archive-action-disabled`: Verify no active tenant UI control can trigger archive, detach, or drop execution.
  3. `audit-ui-view-archived-files`: Verify the `/audit` page displays already archived partition files when metadata exists.
  4. `audit-ui-download-signed-url`: Verify that clicking an existing file's download link retrieves a signed URL.
  5. `audit-ui-download-headers`: Verify an existing downloaded file has correct content-type (e.g., text/csv or application/json) and headers.
- **Feature 3: Finanzmodul (Wirtschaftsplan)**
  1. `finanz-view-page`: Verify the `/wegs/[id]/finanzen` page and creation form are accessible.
  2. `finanz-fill-form`: Verify the form accepts year, description, and total annual costs.
  3. `finanz-calculate-hausgeld`: Verify the UI dynamically calculates and displays monthly Hausgeld per unit based on Miteigentumsanteile (MEA).
  4. `finanz-submit-plan`: Verify clicking "Speichern" creates the Wirtschaftsplan and redirects to detail/list.
  5. `finanz-list-plans`: Verify that saved Wirtschaftspläne are listed on the finanzen overview.
  6. `finanz-edit-plan`: Verify a saved Wirtschaftsplan can be opened from the overview, renamed, and saved.
  7. `finanz-delete-plan-ui`: Verify a saved Wirtschaftsplan can be deleted from the edit page and disappears from the overview.
- **Feature 4: Sollstellung Generation**
  1. `sollstellung-generate-on-save`: Verify saving a Wirtschaftsplan automatically creates 12 monthly Sollstellung entries for each unit.
  2. `sollstellung-verify-amounts`: Verify Sollstellung entry amounts match the calculated monthly Hausgeld (Gesamtkosten * (Unit MEA Zähler / WEG MEA Nenner) / 12).
  3. `sollstellung-view-details`: Verify that monthly Sollstellungen are displayed in the unit details page.
  4. `sollstellung-no-duplicates`: Verify repeated generator calls do not duplicate existing Sollstellungen for the same plan/unit/month.
  5. `sollstellung-history-preserved`: Verify changing plan cost/name metadata does not rewrite existing Sollstellung rows.
- **Feature 5: RLS Security Constraints**
  1. `rls-wp-select-isolated`: Verify Tenant A cannot read Tenant B's Wirtschaftspläne.
  2. `rls-wp-insert-isolated`: Verify Tenant A cannot insert Wirtschaftspläne for Tenant B's WEGs.
  3. `rls-sollstellung-select-isolated`: Verify Tenant A cannot read Tenant B's Sollstellungen.
  4. `rls-sollstellung-direct-writes-blocked`: Verify direct inserts/updates to `sollstellung` are blocked by the pending `0040` contract, including cross-tenant attempts.
  5. `rls-anonymous-blocked`: Verify unauthenticated requests to read/write these tables are blocked by Postgres RLS.

### Tier 2: Boundary & Corner Cases
- **Feature 1: Audit Log Cold-Storage Readiness (Backend)**
  1. `audit-cold-storage-edge-at-threshold`: Test boundary partition at the archive threshold.
  2. `audit-cold-storage-edge-before-threshold`: Test boundary partition just before the archive threshold (not archivable).
  3. `audit-cold-storage-nonexistent-partition`: Attempt destructive action against a nonexistent partition name and verify it is blocked without side effects.
  4. `audit-cold-storage-empty-partition`: Verify empty old partitions are listed as candidates without implying archive/drop execution.
  5. `audit-cold-storage-no-export-job`: Verify no tenant-accessible export path is available before the privileged export + manifest + HMAC-verify job exists.
- **Feature 2: Audit Log Cold-Storage UI**
  1. `audit-ui-expired-signed-url`: Verify that accessing an expired signed URL is rejected.
  2. `audit-ui-no-concurrent-archive-clicks`: Verify no enabled "Archivieren" control is rendered, so double-click archive execution is impossible.
  3. `audit-ui-empty-archive-list`: Verify friendly empty state renders when no archivable partitions exist.
  4. `audit-ui-large-partition-download`: Verify handling and downloading of large partition files.
  5. `audit-ui-special-characters-partition`: Verify handling of partition names containing non-standard date formats or characters.
- **Feature 3: Finanzmodul (Wirtschaftsplan)**
  1. `finanz-wp-invalid-year`: Verify validation errors for negative or far future years.
  2. `finanz-wp-negative-gesamtkosten`: Verify validation errors for zero or negative annual costs.
  3. `finanz-wp-zero-mea`: Verify unit with MEA Zähler of 0 calculates monthly Hausgeld as 0 without divide-by-zero.
  4. `finanz-wp-unaligned-mea`: Verify calculation works correctly when unit MEA sum does not equal WEG MEA Nenner.
  5. `finanz-wp-large-costs`: Verify overflow and decimal precision handling for very large annual costs.
- **Feature 4: Sollstellung Generation**
  1. `sollstellung-partial-year`: Verify 12 months are generated even if creating a plan mid-year.
  2. `sollstellung-round-off`: Verify monthly Hausgeld rounding (e.g., 1000 € / 3 units / 12 months -> 27.78 € / month) is mathematically sound.
  3. `sollstellung-unit-no-mea`: Verify units with missing MEA configurations are handled gracefully.
  4. `sollstellung-overlapping-years`: Verify plans for adjacent years generate independent Sollstellung entries.
  5. `sollstellung-multiple-units`: Verify bulk creation performance and UI loading indicators for WEGs with 100+ units.
- **Feature 5: RLS Security Constraints**
  1. `rls-bypass-rpc-check`: Verify direct invocation of `detach_and_drop_partition` is blocked because the destructive RPC contract is disabled by `0041`.
  2. `rls-cross-tenant-update`: Verify database rejects direct updates of another tenant's rows.
  3. `rls-schema-tampering`: Verify resistance to SQL injection in parameters.
  4. `rls-tenant-header-spoofing`: Verify resistance to JWT/tenant header manipulation.
  5. `rls-sollstellung-direct-write-lockdown`: Verify direct same-tenant and cross-tenant INSERT/UPDATE/DELETE against `sollstellung` are rejected.

### Tier 3: Cross-Feature Combinations (Pairwise Coverage)
1. `cross-audit-and-finanz`: Creating a Wirtschaftsplan generates audit events that can be listed as future cold-storage candidates without triggering tenant-side archive/detach/drop.
2. `cross-finanz-and-sollstellung`: Modifying a Wirtschaftsplan after generation preserves existing Sollstellung entries and requires a future Nachtrag/Korrektur workflow for financial changes.
3. `cross-rls-and-sollstellung`: Verify tenant isolation blocks cross-tenant access to Sollstellung entries in lists, details, and direct queries.
4. `cross-audit-ui-and-rls`: Non-admin users are blocked (403/Forbidden) from accessing the `/audit` page or running cold-storage RPCs.
5. `cross-finanz-and-mea-unit-changes`: Modifying Miteigentumsanteile (MEA) for a unit does not recalculate/regenerate Sollstellungen for existing plans.

### Tier 4: Real-World Application Scenarios
1. `scenario-year-end-closing-and-readiness`: Admin reviews logs older than 24 months and existing archive downloads, confirms destructive archive actions are disabled, and then creates a new Wirtschaftsplan and generates Sollstellungen for the upcoming fiscal year.
2. `scenario-new-weg-onboarding`: onboarding a new WEG with units, allocating Miteigentumsanteile (MEA), creating a new Wirtschaftsplan, and verifying Hausgeld calculations and Sollstellung generations.
3. `scenario-multi-tenant-simultaneous-billing`: Tenant A and Tenant B concurrently perform financial planning and cold-storage operations, verifying complete data separation and zero interference.
4. `scenario-audit-trail-of-financial-actions`: Creating and modifying Wirtschaftspläne creates corresponding audit events, verifying the integrity of the audit trail.
5. `scenario-correction-of-financial-plan`: Corrections after Sollstellung generation are append-only future scope; existing rows stay unchanged and the UI must surface that a Nachtrag/Korrektur is required.

## Coverage Thresholds
- **Tier 1**: ≥5 tests per feature (Total 25 tests)
- **Tier 2**: ≥5 tests per feature (Total 25 tests)
- **Tier 3**: pairwise coverage of major feature interactions (Total 5 tests)
- **Tier 4**: ≥5 realistic application scenarios (Total 5 tests)
- **Total Minimum**: 60 E2E test cases
